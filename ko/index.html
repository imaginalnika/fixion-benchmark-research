한 눈에 보기

예: 플레이어가 바에서 “Hey bartender, what's going on?”이라고 말하면, 바텐더 Mara는 카운터 안쪽으로 플레이어 맞은편 칸 (11,2)까지 걸어와 말을 건네야 합니다. 예전 저가 모델은 코드는 멀쩡히 쓰고도 Mara를 제자리에 세워 두었습니다. 이런 실수를 싸고 믿을 만하게 잡아내는 방법이 이 리서치의 주제입니다.

1 · 좋은 벤치마크와 데이터

공개 벤치마크는 오염·포화·라벨 오류 때문에 후보를 거르는 데만 쓰고, 결정은 우리 케이스로 만든 비공개 eval로 합니다.

결과의 상한은 손으로 쓴 시드 데이터가 정하므로, 증류 전에 eval부터 고정합니다.

2 · 정성 평가를 믿을 만하게

코드로 확인할 수 있는 것은 코드로 확인하고, 취향만 LLM 저지에게 “1–10점” 대신 작은 예/아니오 질문으로 맡깁니다.

저지는 Josh의 pass/fail 라벨로 TPR/TNR과 κ를 잰 뒤에만 믿습니다.

3 · Fixion에 적용

채점은 L0 파싱 → L1 월드 상태 체크 → L2 예/아니오 저지 → L3 페르소나 비교의 네 단계이고, 실제 맵 위 시드 케이스 26개(Josh 6 + 신규 20)로 시작합니다.

L1 통과는 “알려진 실패 없음”일 뿐이므로, 사람이 직접 돌려 보는 단계가 반드시 필요합니다.

읽기 전에 꼭 알아 둘 점

  • 예비 리서치입니다. 케이스가 26개뿐이므로 작은 차이(N≈25에서 약 15점 미만)는 노이즈입니다.
  • X 조사는 표본이 작습니다. 쿼리 6개, 포스트 ~150개, 검색 순위 그대로입니다.
  • 선행 사례: 검토한 논문 중 컷신·NPC 연출 벤치마크는 없었습니다. Fixion 벤치마크는 직접 정의합니다.
  • 저지는 검증 전에는 믿지 않습니다. LLM 저지, 싼 분류기, 키워드 체크 모두 Josh 라벨로 TPR/TNR과 κ를 잰 뒤에 숫자를 씁니다.
  • 스플릿은 seed_id 단위입니다. 변형 케이스는 원본의 seed_id를 물려받으므로 한 시드가 dev와 test에 나뉘지 않습니다. 공개분은 dev 12 / test 14입니다.
  • hidden 스플릿은 오프라인에만 둡니다. v0.1의 hidden 케이스 3개는 이 공개 페이지에 올리면서 test로 옮겼습니다. 진짜 hidden 케이스는 새로 써서 사이트, 리포, 프롬프트 어디에도 넣지 않습니다.
  • 점수마다 프롬프트 버전, 오퍼레이션 계약 버전, 재시도 정책을 함께 기록합니다.

1부. 벤치마크, eval, 데이터

1.1 용어 정리

  • 벤치마크(benchmark). 모델을 서로 비교하기 위해 고정한 문제 세트와 채점 규칙입니다. 발전 추적에도 씁니다(BetterBench, arXiv 2411.12990) [H]. 모두가 같이 쓰는 공용 자입니다.
  • eval(제품 eval). 우리 문제로 만든 우리만의 시험입니다. 우리 문제에 맞춘 전용 자입니다. Hamel Husain은 세 단계로 나눕니다(Your AI Product Needs Evals) [M].
    • (1) 유닛 테스트처럼 쓰는 assertion
    • (2) 사람과 모델의 평가
    • (3) A/B 테스트
  • 오염(contamination). 시험 문제가 학습 데이터에 섞여 점수가 부풀려지는 현상입니다(LiveBench, arXiv 2406.19314; contamination survey, arXiv 2406.04244) [H].
  • 포화(saturation). 상위 모델 점수가 모두 너무 높아져 벤치마크가 모델을 더 구분하지 못하는 상태입니다. 조사한 LLM 벤치마크 60개 중 거의 절반이 이 상태였고, 오래된 벤치마크일수록 심했습니다(When AI Benchmarks Plateau, arXiv 2602.16763, 초록) [H].
  • 굿하트 법칙(Goodhart's law). "When a measure becomes a target, it ceases to be a good measure"(Thomas & Uminsky, arXiv 2002.08512) [H].
    ↳ 지표를 목표로 삼는 순간 그 지표는 망가집니다.
  • capability eval과 regression eval.
    • capability eval: 현재 실력을 재는 시험입니다. 처음에는 통과율이 낮고 올라갈 여지가 있습니다.
    • regression eval: 거의 100% 통과하는 시험입니다. 실력 퇴보를 잡아냅니다.
    • capability eval이 포화되면 regression 세트로 "졸업"시킵니다(Anthropic, Demystifying evals for AI agents) [M].
  • pass@k와 pass^k.
    • pass@k: k번 시도해 한 번이라도 성공할 확률입니다(Codex paper, arXiv 2107.03374) [H].
    • pass^k: k번 시도해 k번 모두 성공할 확률입니다(tau-bench, arXiv 2406.12045) [H].
    • 게임에서 플레이어는 각 장면을 한 번만 봅니다. 그래서 매번 잘하는지(pass^k)가 중요합니다.
  • 시드 세트, 골든 세트, 홀드아웃 세트.
    • 시드 세트(seed set): 데이터를 불리기 위해 사람이 손으로 쓴 작은 세트입니다. Self-Instruct는 시드 태스크 175개로 시작했습니다(arXiv 2212.10560) [H].
    • 골든 세트(golden set): 입력과 신뢰할 수 있는 정답을 함께 모은 세트입니다. 현업 용어이며, 논문에서 정해진 정의는 찾지 못했습니다(의견).
    • 홀드아웃 세트(held-out set): 학습에도 프롬프트 튜닝에도 절대 쓰지 않는 데이터입니다.

1.2 좋은 벤치마크의 조건

벤치마크는 측정 도구입니다. 온도계를 평가할 때와 같은 질문을 던지면 됩니다. 재려는 것을 제대로 재는가, 눈금이 맞는가, 오차는 얼마인가, 누가 꼼수로 숫자를 올릴 수 있는가.

근거

  • BetterBench는 벤치마크 24개를 모범 사례 46개로 채점했습니다. 설계, 구현, 문서화, 유지보수, 은퇴까지 모두 봤습니다(초록; 전문) [H].
    • 결론은 "large quality differences"였습니다.
      ↳ 벤치마크마다 품질 차이가 큽니다.
    • 대부분 통계적 유의성을 보고하지 않습니다.
    • 24개 중 17개는 쉽게 돌릴 수 있는 재현 스크립트가 없습니다.
    • MMLU가 최하점(5.5), GPQA는 11.0이었습니다.
  • 포맷을 조금만 바꿔도 점수가 움직입니다. MMLU에서 "(A)"를 "(1)"로 바꾸거나 공백 하나만 넣어도 "can lead to a ~5% change in accuracy"였습니다. Anthropic이 BBQ를 처음 돌렸을 때는 "technically unbiased, but … completely useless"라는 결과가 나왔습니다. 모델이 아예 대답을 하지 않았기 때문입니다(Anthropic, Challenges in evaluating AI systems) [H].
    ↳ 정확도가 ~5% 바뀔 수 있습니다 / 편향은 없지만 쓸모도 없습니다.
  • 정답 라벨이 틀릴 수 있습니다. MMLU 문제의 6.49%에 오류가 있는 것으로 추정되고, 분석한 Virology 문제는 57%에 오류가 있었습니다(MMLU-Redux, arXiv 2406.04127) [H].
  • 오차 막대(error bar) (Miller, Adding Error Bars to Evals, arXiv 2411.00640) [H]:
    • 표준오차(SE)를 함께 보고합니다.
    • 문제가 묶음으로 나오면 SE를 묶음 단위로(clustered) 계산합니다. 이 값은 "can be over 3X larger than naive"입니다.
      ↳ 단순 계산보다 3배 넘게 커질 수 있습니다.
    • 모델 간 차이는 같은 문제끼리 짝지어(paired) 비교합니다.
    • 검정력 분석(power analysis)을 먼저 합니다. 논문 예시에서는 3점 차이를 잡는 데 문제가 약 969개 필요했습니다.
  • 좋은 태스크의 조건 (Anthropic agent evals) [M]:
    • 전문가 두 명이 pass/fail에 동의해야 합니다.
    • 통과율이 0%에 가까우면 태스크와 채점기 버그부터 의심합니다.
    • 과정이 아니라 결과를 채점합니다.
  • 포화 방지에 도움이 된 것. 전문가가 직접 고른 문제는 포화에 잘 버텼습니다. 반면 테스트 데이터 비공개는 보호 효과가 없었습니다(arXiv 2602.16763) [H].

체크리스트(정리): 재려는 것을 재는가(construct validity) · 라벨 정확성 · 문제의 모호성 · 채점의 견고함 · 오차 막대와 충분한 문항 수 · 기준점(랜덤 하한, 사람 기준선) · 오염 방어 · 상승 여지(headroom) · 재현성 · 실제 용도와의 관련성.

1.3 유명 벤치마크는 어떻게 만들었나

HumanEval (2021) 문제 164개를 손으로 직접 작성("It is important for these tasks to be hand-written"). GitHub 학습 데이터에 기존 문제가 있을 수 있기 때문 유닛 테스트(문제당 ≈7.7개), pass@k 오염이 걱정되면 손으로 작성 arXiv 2107.03374 [H]

Dynabench (2021) 모델이 틀리는 예시를 사람이 작성 사람-모델 루프 적대적 수집 arXiv 2104.14337 [H]
HLE (2025) 전문가가 쓴 문제 2,500개. MMLU 점수가 90%를 넘어서 제작 정확한 답 상승 여지를 남기도록 설계 arXiv 2501.14249 [H]
LiveBench / LiveCodeBench 매달 새 문제 / 날짜가 찍힌 대회 문제 객관식 자동 채점 새 문제로 오염 회피 2406.19314, 2403.07974 [H]
ARC-AGI-2 공개, 준비공개, 비공개 eval 세트 각 120개. 남긴 문제는 모두 2명 이상이 2번 안에 푼 문제 그리드 완전 일치 비공개 스플릿 + 사람이 풀 수 있는지 필터 arcprize.org [M]

의견: 대부분 비슷한 순서로 만듭니다.

  1. 실제 태스크가 나오는 곳을 고릅니다.
  2. 정답을 기계로 확인할 수 있게 만듭니다.
  3. 서로 독립인 전문가가 검증하고, 의견이 갈리는 문제는 뺍니다.
  4. 기준선(baseline)을 잽니다.
  5. 테스트 세트를 보호합니다.
  6. 하네스를 공개합니다.

흔한 실패는 3번을 건너뛸 때 생깁니다. MMLU의 라벨 오류와 SWE-bench에 "Verified" 버전이 따로 필요했던 이유가 여기에 있습니다.

1.4 벤치마크, 실제로 얼마나 중요할까

오염.

  • 근거: GSM8k를 새로 다시 쓴 GSM1k에서 일부 모델 계열은 점수가 최대 8% 떨어졌고 "systematic overfitting"을 보였습니다. 프런티어 모델 상당수는 과적합이 거의 없었습니다(arXiv 2405.00332) [H].
    ↳ 체계적인 과적합.
  • 의견: 오염은 실제로 있습니다. 다만 모델마다 정도가 달라 리더보드만으로는 판단할 수 없습니다. Josh의 비공개 컷신 세트는 공개하거나 프롬프트에 붙여 넣지 않는 한 구조상 오염될 수 없습니다.

포화.

  • 근거: 벤치마크 60개 중 약 절반이 포화됐습니다(2602.16763) [H].
  • 근거: SWE-bench 공동 제작자의 HN 댓글: "All benchmarks and benchmark paradigms eventually become saturated"(ofirpress, HN) [H].
    ↳ 모든 벤치마크는 결국 포화됩니다.
  • 의견: Josh에게 포화는 좋은 소식입니다. dev 세트가 포화되면 regression으로 옮기고 더 어려운 케이스를 쓰면 됩니다.

굿하트.

  • 근거: 지표만 과하게 최적화하면 "manipulation, gaming, a myopic focus on short-term goals"가 생깁니다. 처방은 여러 지표와 정성적 설명을 함께 쓰는 것입니다(Thomas & Uminsky) [H].
    ↳ 조작, 꼼수, 단기 목표에만 매몰.
  • 근거: 현재 진행형 사례가 LMArena입니다. Karpathy는 랩들이 "better LM Arena models … Possibly something with a lot of nested lists, bullet points and emoji"를 얻게 된다고 썼습니다(X post, read in full) [H].
    ↳ Arena 점수만 좋은 모델, 아마 중첩 목록·글머리표·이모지 범벅. LMArena는 해당 논문의 주장에 반박했습니다(@arena) [H].
  • 의견: 저지 점수 하나만 올리려 하면 프롬프트가 그 저지의 비위를 맞추는 법을 배웁니다. 좁은 체크를 여러 개 두고, 장면은 계속 직접 읽습니다.

작은 N의 노이즈.

  • 근거: Miller의 검정력 분석에 따르면 3점 차이를 잡으려면 문제가 ≈1,000개 필요합니다(2411.00640) [H].
  • 근거: Hamel은 저지 검증 시 실패 유형마다 라벨 단 예시가 약 100개 있으면 좋고, 약 60개 미만이면 신뢰구간(CI)이 너무 넓어진다고 합니다(Using LLM-as-a-Judge) [M].
  • 의견: 케이스 26개로 큰 퇴보(80% → 40%)는 잡지만 80% → 75%는 못 잡습니다. §2.5를 참고하십시오.

eval 주도 개발, 그리고 "evals are the new unit tests".

  • 근거: OpenAI 가이드: "Adopt eval-driven development: Evaluate early and often"(OpenAI eval best practices) [H].
    ↳ 일찍, 자주 평가합니다.
  • 근거: Anthropic: "20-50 simple tasks drawn from real failures is a great start"(Anthropic) [H].
    ↳ 실제 실패에서 뽑은 간단한 태스크 20–50개면 시작으로 충분합니다.
  • 근거: Hamel과 Shankar: "Error analysis is the most important activity in evals"(Evals FAQ) [H].
    ↳ eval에서 가장 중요한 활동은 오류 분석입니다.
  • 근거: Hamel: "Unit tests for LLMs are assertions"(Your AI Product Needs Evals) [H].
    ↳ LLM의 유닛 테스트는 assertion입니다.
  • 이 말의 원작자: "evals are the new unit tests"를 처음 한 사람은 찾지 못했습니다. Medium 글 제목 하나와 Maven 페이지 하나만 나왔습니다(스니펫만, [L]). 실제로 읽은 것 중 가장 가까운 글은 Sentry의 Evals are just tests입니다 [M].
  • 의견: 비유가 맞지 않는 부분.
    • eval은 결과가 매번 달라서 K번 돌려야 합니다.
    • 참/거짓이 아니라 정도의 문제라서 기준선이 필요합니다.
    • 실행마다 비용이 들어서 단계별로 걸러야 합니다.

결론(의견). 공개 벤치마크는 모델 후보를 고를 때 어느 정도 중요합니다. 우리 eval은 결정적으로 중요합니다. eval이 없으면 프롬프트가 실제로 나아졌는지, 운 좋은 샘플이었는지 구분할 수 없습니다. 증류한 모델이 실력을 배웠는지 말투만 따라 했는지도 알 수 없습니다.

1.5 데이터는 얼마나 중요할까: "손으로 못 만드는 건 절차적으로도 못 만든다"

격언의 출처.

  • 근거: 꽤 찾아봤지만 "you cannot procedurally generate what you can't handcraft"라는 문장 그대로의 출처는 없었습니다. 업계에 도는 말로 보면 됩니다[못 찾았다는 사실은 H].
  • 가장 가까운 실제 출처:
    • Kate Compton: "The most reliable generators are the ones where you can concretely describe constraints". 타일 기반 생성기가 잘 되는 이유도 "each possible tile has to be authored by a human"이기 때문이라고 합니다. 방법을 고르기 전에 "How would a human solve this problem?"부터 물으라고 합니다(So you want to build a generator) [H].
      ↳ 제약을 구체적으로 기술할 수 있는 생성기가 가장 믿을 만합니다 / 타일은 하나하나 사람이 만들어야 합니다 / 사람이라면 이 문제를 어떻게 풀겠습니까?
    • Emily Short: 절차적 생성은 "isn't a substitute for designing content"이며 "a way of designing content — one that is often at least as labor-intensive"라고 합니다(Bowls of Oatmeal) [H].
      ↳ 콘텐츠 디자인을 대신하지 않습니다. 그 자체가 디자인 방법이며, 손이 덜 가지도 않습니다.
    • Compton의 "10,000 bowls of oatmeal" 문제: 결과물이 기술적으로는 모두 달라도 보는 사람에게는 똑같아 보일 수 있습니다("Perceptual uniqueness is the real metric").
      ↳ 진짜 지표는 체감상 다른지 여부입니다.

ML에서도 같습니다: 시드가 상한을 정합니다.

  • Self-Instruct, Alpaca, Evol-Instruct는 모두 같은 사람이 쓴 시드 태스크 175개에서 출발했습니다(Self-Instruct; Alpaca; WizardLM) [H].
  • LIMA: 잘 고른 예시 1,000개만으로 43%의 경우에서 GPT-4와 같거나 더 낫다는 평가를 받았습니다. 데이터를 두 배로 늘려도 효과가 없었고, 다양성과 품질이 효과를 냈습니다(arXiv 2305.11206) [H].
  • phi-1: 필터링이 중요했습니다(HumanEval 12.19% → 17.68%). 합성 데이터를 단순한 프롬프트로 뽑으면 "a very homogeneous and redundant dataset"이 나옵니다(arXiv 2306.11644) [H].
    ↳ 서로 비슷하고 중복이 많은 데이터셋.
  • 모델 붕괴(model collapse): 모델이 만든 데이터로 반복 학습하면 분포의 꼬리(드문 케이스)가 사라집니다. 세대마다 원래 사람 데이터 10%를 남기면 성능 저하가 작았습니다(Shumailov et al., Nature 2024, OA PDF) [H].

템플릿 변형은 효과가 있고, 약점도 드러냅니다.

  • GSM-Symbolic은 GSM8K 문제를 템플릿으로 바꿨습니다. 이름만 바꿔도 정확도가 흔들렸고, 숫자를 바꾸면 더 떨어졌습니다. 무관한 문장 하나를 끼워 넣으면 최대 65%까지 떨어졌습니다(arXiv 2410.05229) [H].
  • CheckList는 테스트를 세 종류로 나눕니다(ACL 2020) [H]:
    • MFT(최소 기능 테스트): 단순하고 목표가 분명한 테스트.
    • INV(불변 테스트): 정답이 바뀌지 않는 수정에는 출력도 바뀌지 않아야 하는 테스트.
    • DIR(방향 테스트): 결과가 어느 방향으로 바뀌어야 하는지 아는 수정.
  • Josh가 말한 "이름 바꾸기, 열 옮기기" 아이디어가 바로 이것입니다.

차원(dimension)을 정해 eval 입력 합성하기.

  • Hamel의 방법(synthetic data FAQ) [H]:
    • 실패 가설에서 차원을 고릅니다.
    • 조합(tuple) ~20개를 손으로 씁니다: "This manual work helps you understand your problem space."
      ↳ 이 수작업을 거쳐야 문제 영역을 이해하게 됩니다.
    • LLM으로 조합을 늘리고, 조합을 실제 입력으로 바꾸는 일은 별도 프롬프트로 합니다.
  • 모델이 쓴 eval도 크라우드 작업자와의 라벨 일치율이 90–100%까지 나왔습니다(Perez et al., arXiv 2212.09251, 초록) [H].

증류보다 eval이 먼저인 이유.

  • 근거: ChatGPT 출력으로 학습한 모방 모델은 크라우드 평가자와 GPT-4에게 꽤 좋은 평가를 받았습니다. 그러나 표적 eval에서는 개선이 거의 없었습니다. "adept at mimicking ChatGPT's style but not its factuality"였습니다(False Promise of Imitating Proprietary LLMs, arXiv 2305.15717) [H].
    ↳ 말투는 잘 따라 하지만 사실관계는 따라 하지 못합니다.
  • 근거: Orca도 같은 함정을 지적합니다. 평가가 엄격하지 않으면 "imitate the style, but not the reasoning process"하는 작은 모델을 과대평가하게 됩니다(arXiv 2306.02707, 초록) [H].
    ↳ 스타일만 따라 하고 추론 과정은 따라 하지 못하는 모델.
  • 의견: Fixion에 적용하면.
    • 증류한 "컷신 베이스 모델"은 겉으로는 Astra 출력처럼 보일 것입니다. # 줄도 깔끔하고 대사도 그럴듯할 것입니다.
    • 중요한 것은 Mara가 실제로 (11,2)에 도착하는지입니다. 이것은 고정한 L1 세트만 알려 줍니다.
    • 학습 데이터를 만들기 전에 test와 hidden 스플릿을 고정합니다. 이 스플릿은 절대 시드로 쓰지 않습니다.

2부. 정성 평가를 믿을 만하게 만들기

2.1 LLM 저지란

정의. 사람 평가자 대신 강한 LLM이 채점하는 방식을 LLM 저지(LLM-as-judge)라고 합니다. MT-Bench / Chatbot Arena에서 GPT-4는 사람 선호와 85% 일치했습니다(무승부 제외). 사람끼리는 81%였습니다(Zheng et al., arXiv 2306.05685) [H].

세 가지 형식(같은 논문) [H]:

  • 쌍대 비교(pairwise): A와 B 중 선택 또는 무승부.
  • 단일 채점(pointwise): 출력 하나에 점수 부여. 저지를 바꾸면 점수가 더 크게 흔들립니다.
  • 정답 참고(reference-guided): 저지가 정답을 보고 채점합니다. 수학에서 GPT-4 저지 실패가 14/20에서 3/20으로 줄었습니다.

주요 저지 시스템:

  • G-Eval: 자동 생성한 CoT 단계를 따라 저지가 양식을 채우고, 확률 가중 점수를 냅니다(arXiv 2303.16634) [H].
  • Prometheus: 루브릭과 정답을 쓰는 오픈 13B 저지입니다. 사람과의 Pearson 상관은 0.897, GPT-4는 0.882였습니다(arXiv 2310.08491, 초록) [H]. Prometheus 2는 쌍대 비교 모드를 추가했습니다(2405.01535, 초록) [H].

2.4 저지를 사람 기준에 맞추기

용어.

  • Cohen's κ = (p_o − p_e)/(1 − p_e): 우연히 일치할 확률을 뺀 일치도입니다. Landis–Koch 기준으로 0.61–0.80은 "substantial", 0.81 이상은 "almost perfect"입니다(이 구간 구분에는 이견이 있습니다). 드문 카테고리에서는 κ가 일치도를 낮게 잡습니다(Wikipedia) [M].
  • TPR/TNR: 실제 실패를 저지가 얼마나 잡는지(TPR), 실제 통과를 얼마나 통과시키는지(TNR)입니다. 예를 들어 장면의 5%만 실패한다면, 무조건 "pass"를 내는 저지도 일치율이 95%입니다. 하지만 쓸모는 없습니다(Hamel) [M].

절차. Hamel [M], Shankar et al. [H], MT-Bench 논문 [H]을 종합했습니다.

  1. 도메인 전문가 한 명(Josh)이 pass/fail 라벨을 답니다. 한 줄 비평도 함께 씁니다.
  2. 라벨을 나눕니다. 약 10–20%는 few-shot 예시, 약 40%는 dev, 약 40%는 test입니다. 클래스마다 30–50개를 목표로 합니다.
  3. dev에서 저지 프롬프트를 고치고, test에서는 딱 한 번만 돌립니다.
  4. TPR, TNR, κ를 보고합니다.
  5. 일주일 뒤 30개를 다시 라벨링해 Josh 본인의 일관성을 잽니다. 이것이 상한입니다. Josh가 자기 자신과 85% 일치한다면 저지에게 95%를 요구할 수 없습니다. MT-Bench에서 사람 간 일치도는 81%였습니다(MT-Bench) [H].
  6. 저지 모델, 생성 모델, 루브릭 중 하나라도 바뀌면 다시 검증합니다.

Hamel은 critique shadowing(전문가 비평을 저지가 따라 배우게 하는 방식)을 세 번 반복해 도메인 전문가와 ">90% agreement"에 도달했다고 합니다(Hamel) [H].

2.5 통계: 케이스가 몇 개 필요하고, 오차는 얼마나 될까

N개 케이스로 잰 통과율도 노이즈가 섞인 추정값입니다. 진짜 통과율이 80%일 때의 불확실성 폭은 다음과 같습니다(계산; Wald·Wilson 구간, 케이스 간 독립 가정).

케이스 수 N SE 95% ± (Wald) Wilson 95% CI
20 0.089 ±0.175 0.58–0.92
25 0.080 ±0.157 0.61–0.91
50 0.057 ±0.111 0.67–0.89
100 0.040 ±0.078 0.71–0.87
200 0.028 ±0.055 0.74–0.85
500 0.018 ±0.035 0.76–0.83

계산 결과.

  • 독립된 두 표본에서 0.80과 0.70을 구분하려면 한쪽에 약 294개씩 필요합니다.
  • 같은 케이스로 짝지어 비교하면 훨씬 적게 듭니다. Miller가 짝 비교를 권하는 이유입니다(2411.00640) [H].
  • 같은 장면이나 같은 NPC에서 나온 케이스는 서로 상관이 있습니다. 따라서 SE는 픽스처 단위로 묶어 계산합니다.

pass^k. 샘플 하나의 통과 확률이 0.8이면 3개 모두 통과할 확률은 0.8³ ≈ 0.51입니다(계산). tau-bench의 retail 도메인에서 pass^8은 25% 미만이었습니다(2406.12045) [H]. 게임에서는 pass^k가 정직한 숫자입니다.

의견: Fixion에는 이 정도 규모면 충분합니다.

  • 시드 26개 × 샘플 K=3이면 큰 고장을 잡고 라벨링을 시작하기에 충분합니다.
  • 추세를 보려면 약 100–200개(시드 + 검수한 변형)면 됩니다.
  • 버전 간 비교는 항상 같은 케이스로 합니다(짝 비교).

A. 벤치마크 일반 (X.1–X.5)

벤치마크를 믿을 수 있게 지키는 방법: 리더보드보다 자체 eval, hill-climbing에 맞서는 홀드아웃, 초록불을 믿기 전에 데이터 읽기, 시드 출처 기록.

X.1 자체 eval을 씁니다: 하네스와 프롬프트도 모델만큼 중요합니다

  • "자체 eval을 돌려라"는 포스트는 많지만 대부분 내용이 얕습니다. 구체적인 것만 추리면:
    • 한 사용자가 분류·추출 작업을 더 새로운 모델에서 추론 수준을 바꿔 가며 다시 돌렸습니다. 결과는 GPT 4.1 Mini보다 일관되게 조금 낮았고, 지시 일부를 들쭉날쭉하게 무시했습니다(post, 전문).
    • "take any and all benchmark numbers with big grains of salt, test on your own evals"(post).
      ↳ 벤치마크 숫자는 전부 걸러 듣고, 자체 eval로 테스트합니다.
    • 커스텀 벤치마크에서 두 모델이 95% 대 53%였다는 포스트(로 보이는 글)에 달린 답글: "public leaderboards don't know your tools, your data or your failure cases"(post; 답글만 봤고, 원래 숫자가 있는 포스트는 보지 못했습니다).
      ↳ 공개 리더보드는 우리 도구, 데이터, 실패 사례를 모릅니다.
  • Fixion에는: 점수마다 프롬프트, 오퍼레이션 계약(operation contract: 쓸 수 있는 op 목록, 인자 수, 제한), 재시도 정책을 함께 기록합니다. Josh의 이전 결과가 바로 리더보드로는 알 수 없는 정보입니다. 코드는 유효했지만 공간 이동을 놓친 사례, 그리고 첫 토큰까지 23초.

X.2 hill-climbing과 홀드아웃: 반복해서 고치는 벤치마크를 지키는 법

  • eval 최적화 포스트에 달린 답글들이 반복해서 홀드아웃 세트를 요구합니다:
    • "hill climbing on your own evals usually drifts toward the evals"(post, 팔로워 3명 계정).
      ↳ 자체 eval로 점수를 올리면 보통 eval 자체에 맞춰집니다.
    • "keep a held-out set you never touch while tuning. If your main set goes up and that one doesn't, you're gaming your own evals"(post).
      ↳ 튜닝 중 절대 건드리지 않는 세트를 둡니다. 메인 세트만 오르면 자기 eval을 속이는 것입니다.
    • "the model now writes the test it later aces"(post; Claude Developers 포스트 아래 냉소적인 답글).
      ↳ 모델이 시험을 쓰고, 나중에 그 시험에서 만점을 받습니다.
  • François Chollet: 공개된 ARC 3 게임을 eval 세트도 학습 세트도 아닌 "demonstration set"이라고 부릅니다. 이 점수로 hidden 세트 점수를 알 수 없다고 합니다(post, 2026-08-14, 좋아요 257; 본문 잘림). 공개/hidden 스플릿에 정직한 이름을 붙인 구체적인 예입니다.
    ↳ 시연용 세트.
  • Fixion에는: dev 케이스는 공개하고 자유롭게 반복합니다. hidden test 스플릿은 사람이든 에이전트든 누구도 튜닝에 쓰지 않으며, 페이지에도 그렇게 적습니다. 이 페이지는 공개이므로 여기 나온 케이스는 사실상 모두 dev 또는 test입니다. hidden 스플릿은 오프라인에만 둡니다.

X.3 데이터와 실패부터 봅니다: 평가기를 과하게 만들지 않습니다

  • Anthropic의 eval 제작 워크플로에 대한 Hamel의 의견: 이 워크플로는 "creates evals before looking at data, and has you correct its mistakes"라고 합니다. 그는 데이터를 먼저 봐야 이해할 수 있고, 무엇을 할지 정할 수 있다고 봅니다(post, 2026-09-29, 좋아요 504; 검색 결과에서 본문 잘림).
    ↳ 데이터를 보기 전에 eval부터 만들고, 그 실수를 사람이 고치게 합니다.
  • Hamel의 다른 포스트:
    • 골드 세트가 낡으면 정기적인 오류 분석으로 새 문제를 찾습니다(post).
    • 실패 유형마다 자동 평가기를 만들지 않습니다. 코드 체크와 LLM 저지는 비용이 다릅니다(post).
    • eval 실행 빈도는 비용과 포화 정도에 따라 정합니다(post).
    • AI eval FAQ를 질문 48개로 업데이트했습니다(post).
  • Fixion의 단계별 계획과 맞는 작은 답글: 버전 관리되는 케이스 30–50개를 만듭니다. 확인 가능한 결과(필수 도구 호출, 최종 상태)는 코드로 보고, 판단이 필요한 곳에만 LLM 저지를 씁니다. 저지는 사람 라벨로 확인한 pass/fail 루브릭을 따릅니다(post, 팔로워 10명 계정).
  • Fixion에는: 첫 dev 실행의 트레이스를 모두 읽는 것이 올바른 첫걸음입니다. L1/L2 체크는 실제로 본 실패 유형에만 추가하고, 실패 유형 목록을 계속 늘립니다.

X.4 초록불이 다 켜져도 게임은 망가져 있을 수 있습니다

  • eval 도구 제작자에게 한 개발자가 단 답글입니다. 벤치마크는 "measures what somebody thought to measure"라고 합니다. 자기 게임은 16/16 초록불이었지만 "visibly broken the second I watched it run, because nobody had written a check for a head that wobbles"였다고 합니다(post; 좋아요 1, 작은 계정, 주제에 맞는 일화).
    ↳ 누군가 재려고 한 것만 잽니다 / 돌려 보자마자 망가진 것이 보였습니다. 흔들리는 머리를 체크하는 코드가 없었습니다.
  • Fixion에는: Josh의 findings 문서가 얻은 교훈("state pass"는 좋은 연기가 아님)과 같습니다. L1 통과를 "좋음"으로 보고하지 않습니다. 트레이스 sanity check는 발견하는 대로 추가하고, 사람이 직접 돌려 보는 단계를 유지합니다.

X.5 합성 데이터와 시드 출처 기록

  • "Synthetic data needs provenance and held-out real evals; otherwise gains can be artifacts of the generator. Log generator/model version, seed, filtering rules, and keep an untouched real slice for regression."(post, 팔로워 77명 계정).
    ↳ 합성 데이터에는 출처 기록과 따로 빼 둔 실제 eval이 필요합니다. 없으면 점수 상승이 생성기의 부산물일 수 있습니다. 생성 모델 버전, 시드, 필터 규칙을 기록하고, 손대지 않은 실제 데이터를 회귀 테스트용으로 남겨 둡니다.
  • Anand Kannappan은 "We cannot write every task by hand"라는 글을 썼습니다. 합성 데이터는 "AI slop"(AI 쓰레기)이 아니며, 전문가가 직접 쓸 수 있는 것보다 훨씬 많은 태스크를 전문성으로 만들 수 있다는 주장입니다(post, 좋아요 88; 포스트와 제목만 봤습니다).
    ↳ 모든 태스크를 손으로 쓸 수는 없습니다.
    • 의견: "손으로 못 만드는 것은 절차적으로도 못 만든다"에 대한 합리적인 반론입니다. 손으로 쓴 부분이 기준점이 되고, 전문가가 생성 방향을 잡습니다.
  • 기억해 둘 정의: 다른 모델 출력으로 SFT 하거나 그 트레이스를 합성 데이터 시드로 쓰는 것은 "is not distillation"이고, 로짓에 reverse KL을 거는 것이 증류라고 합니다(post).
    ↳ 증류가 아닙니다.
  • "procedural generation"과 "handcrafted"로 검색하면 게임 마케팅 포스트와 오픈 월드를 둘러싼 팬들의 논쟁만 나왔습니다. 이 격언을 벤치마크에 적용한 글은 없었습니다. 그래서 이 원칙의 근거는 §1.5–1.6의 논문과 Hacker News 스레드뿐입니다.
  • Fixion에는: 합성 케이스마다 생성 모델, 시드 케이스, 변형 종류, 필터를 기록합니다. 변형 케이스에는 원본 수작업 케이스를 가리키는 seed_id를 붙입니다. dev/test는 seed_id 단위로 나눠서, 한 시드의 변형이 스플릿 양쪽에 걸치지 않게 합니다. (시드 단위 분할은 출처 기록 조언에서 추론한 것이며, X에서 그대로 인용한 내용이 아닙니다.)

B. 정성 평가 벤치마크와 LLM 저지 (X.6)

X.6 저지도 분류기입니다: 믿을 수 있는 라벨로 검증합니다 (여러 번, 강하게 나온 주장)

  • Hamel Husain: LLM 저지는 "is also [a] classifier"라고 합니다. 사람 라벨로 테스트하고, 과적합하지 말라고 합니다(post, 2026-09-20, 좋아요 465).
    ↳ 저지도 분류기입니다.
    • 후속 포스트: "No single classifier is best for every eval". 사람 라벨로 검증하면 정확도와 비용 사이에서 고르기 쉬워진다고 합니다(post).
      ↳ 모든 eval에 최선인 분류기는 없습니다.
    • "Jev and an LLM judge are both classifiers that you should validate against trusted labels"(post, 좋아요 221).
      ↳ Jev와 LLM 저지 모두 분류기이므로 믿을 만한 라벨로 검증해야 합니다.
    • 공개 벤치마크가 아니라 제품별 eval을 말하는 것이라고 덧붙였습니다(post).
  • 작은 계정들도 같은 말을 합니다:
    • 사람 기준 보정 없는 저지는 "opinion laundering"이라고 합니다(post).
      ↳ 의견 세탁.
    • 방법 하나: 같은 답을 같은 루브릭으로 저지를 새로 호출해 다시 채점하고, 판정이 갈린 것을 살펴보고, 따로 빼 둔 사람 라벨과 비교합니다(post).
    • 사람과의 일치도 80% 이상을 목표로 한 골든 세트(post).
  • Jev 관련(검증되지 않음, 벤더 쪽 주장).
    • 여러 포스트가 TypeSafe AI의 Jev를 텍스트 대신 분류 결과와 확률만 내는 판정 전용 모델로 설명합니다(post).
    • 한 포스트는 LLM 저지 비용의 1/80 미만으로 정확도 100%라고 주장합니다(post).
    • 원래 기사는 읽지 않았습니다.
  • 언급된 함정(스니펫 수준):
    • 저지가 맞는 판정을 틀린 이유로 낼 수 있습니다. Netflix의 발견으로 소개됩니다(post).
    • 테스트 입력을 만든 모델이 독립 지표로 봐도 계속 유리했습니다(post).
    • 저지 간 상관을 모델링해 합치는 방식이 다수결보다 9–14% 나았습니다(post; 뉴스 봇의 논문 요약 포스트).
  • Fixion에는: 먼저 직접 라벨을 달고, 그 라벨로 L2 저지의 일치도(TPR/TNR, κ)를 잰다는 계획을 뒷받침합니다. 예/아니오 질문 상당수는 싼 분류기형 저지로도 가능해 보입니다. 그래도 다른 저지와 똑같이 Josh 라벨로 검증합니다.

X.7 덧붙임: LLM NPC 관련 포스트

  • 작은 계정이나 벤더의 포스트입니다:
    • "Ask an AI NPC the same question three different ways in a row. Most break by attempt two ... nobody tested for consistency under pressure"(MistScale; 벤더 포스트, 좋아요 6).
      ↳ AI NPC에게 같은 질문을 세 가지로 바꿔 연달아 물으면 대부분 두 번째에 무너집니다. 압박 속 일관성은 아무도 테스트하지 않았습니다.
    • "LLMs shouldn't be the NPC's brain. They should be its mouth". 계획과 협동은 결정론적 규칙에 맡기자는 주장입니다(post; 팔로워 3명 계정, 근거 없음).
      ↳ LLM은 NPC의 뇌가 아니라 입이어야 합니다.
    • 한 개발자는 에이전트로 NPC 대사와 조우 변형을 오프라인에서 미리 쓰고, 런타임은 결정론적으로 유지합니다(post).
    • "latency and cost are the real design constraints, not the writing"(post).
      ↳ 진짜 설계 제약은 글이 아니라 지연 시간과 비용입니다.
  • 게임을 하는 에이전트를 벤치마크로: 찾은 것은 E2B와 Prime Intellect의 에이전트가 Factorio를 하는 장기 테스트 하나입니다(post, 좋아요 211). 벤치마크라기보다 데모입니다.
  • Fixion에는:
    • "바꿔 물어도 일관된가"는 페르소나·바꿔 말하기 변형(의도는 같고 표현이나 언어만 다름)에 대응합니다. pass^k 같은 지표로 채점합니다.
    • "뇌 말고 입"은 테스트해 볼 설계 옵션이지 결과가 아닙니다.

X.8 계획에서 바뀐 것

  1. 점수마다 프롬프트, 오퍼레이션 계약, 재시도 정책을 저장합니다(X.1 → §3.6).
  2. 어떤 튜닝 루프도 보지 않는 hidden test 스플릿을 두고, 공개 세트에는 dev/test라고 표시합니다(X.2 → §3.4).
  3. L1 통과는 "좋음"이 아니라고 명시합니다. 트레이스 sanity check와 직접 돌려 보는 단계를 넣습니다(X.4 → §3.2, §3.5).
  4. seed_id를 추가하고 시드 단위로 스플릿을 나눕니다. 합성 케이스는 생성 모델, 시드, 변형, 필터를 기록합니다(X.5 → §3.1, §3.4).
  5. 싼 분류기 저지를 포함해 모든 저지를 Josh 라벨로 검증합니다(X.6 → §3.4).

설계 이유(의견).

  • seed_id(v0.2 신규). 손으로 만든 케이스는 각자 자기 자신이 시드입니다(seed_id = id, 현재 26개 전부). 변형·합성 케이스는 새 id를 받지만 부모의 seed_id를 물려받고, 생성 모델·변형 종류·필터를 provenance에 남깁니다. dev/test/hidden은 seed_id 단위로 정합니다. 따라서 한 시드의 변형들이 스플릿 양쪽에 걸치지 않습니다(출처: §X.5; 시드 단위 분할은 우리 추론입니다).
  • 픽스처는 리포의 실제 맵을 그대로 씁니다(bar 28×13, festival, bandits). 하네스가 SceneRuntime으로 월드를 만들고, 실제 파서와 스케줄러로 리플레이할 수 있습니다.
  • 좌표와 ID를 모두 적습니다. ID는 런타임의 행 우선 스캔 순서를 따릅니다(예: bar_chair_7 = (11,9)). 그래야 변형을 기계적으로 적용할 수 있습니다.
  • assertion은 코드가 아니라 선언으로 씁니다. 리뷰, diff, 변형이 모두 쉬워집니다. 어휘는 작습니다.
    • 위치: ends_at, ends_within, stays_in, unchanged_position, not_at_end, ends_closer_than_start.
    • 자세·소유: seated, standing, item_owner.
    • 말하기·듣기: said(heard_by_listener 포함), silent, speech_lang, speech_volume, speech_chars_max, not_heard_by, not_repeat.
    • op·구조: never_op, op_used, last_instruction, following, distinct_actors_acting, max_instructions, before, any_of.
  • 심각도. critical이 실패하면 케이스가 실패합니다. soft는 보고만 하고 실패로 치지 않습니다.
  • 전역 저지 질문(G1–G4)은 모든 케이스에 붙습니다.
    • G1: 주석 ≠ 실제 효과.
    • G2: 알 수 없는 정보를 아는 것처럼 행동하지 않는가.
    • G3: 반응이 입력에 걸맞은가.
    • G4: 최종 상태와 모순되지 않는가.

3.2 (b) 단계별 채점 구조

레이어 확인 대상 방법 비용 신뢰도
L0 파싱/인자 수 #과 명령 줄이 번갈아 나오는가, 아는 수신자·아는 op인가, ARITY, 인자 타입, 명령 ≤24개, 보이는 글자 140자, 유효한 gesture, 위치 기반 JSON 인자 리포의 SceneProgram.parse를 그대로 사용. 벤치마크와 게임의 판정이 항상 일치 ~0 아주 높음
L1 월드 상태 리포의 스케줄러와 월드 규칙으로 리플레이한 이벤트 트레이스(시간별 위치, 착석, 소유, 대사와 들은 사람, follow/hold 상태, 런타임 에러)에 케이스 assertion 적용 트레이스를 읽는 결정론적 Ruby/Python 체커 ~0 높음. 단, assertion으로 적어 둔 것만 확인
L2 예/아니오 저지 케이스 질문 + G1–G4. 원본 코드가 아니라 렌더링한 이벤트 로그를 보고 YES/NO/UNKNOWN으로 답변, 근거 인용 다른 계열의 싼 저지 또는 혼합 3인 패널. 판정이 갈리면 상위 단계로 케이스당 작은 모델 호출 ≈ 1회 중간. Josh 라벨로 보정한 뒤에만
L3 페르소나/톤 쌍대 비교 (i) 페르소나 맞히기: 페르소나 A, B와 트레이스 두 개를 주고 어느 쪽이 A의 것인지 판정. (ii) A/B 품질: 어느 트레이스가 페르소나와 장면에 더 맞는지 판정 두 순서로 모두 질문, 일관될 때만 승리. 나중에 모델 간 Bradley-Terry 쌍당 호출 2회 중간~낮음. 합격선이 아니라 추세용

L1 통과는 "좋다"는 뜻이 아닙니다. L1은 누군가 assertion으로 적어 둔 것만 확인합니다. Josh가 본 Astra "통과" 출력 32개도 똑같이 좋은 장면 32개가 아니었습니다. X에서는 한 개발자가 16/16 초록불을 받았지만 실행하자마자 망가진 부분이 보였다고 했습니다(§X.4). 그래서 L1 결과는 "알려진 실패 없음"으로만 보고하고, 품질이라고 부르지 않습니다. 안전장치는 두 가지입니다.

  • 트레이스 sanity check. 실패를 발견할 때마다 추가하고, 모든 케이스에 적용합니다. 예를 들어 캐릭터의 무의미한 왕복, 제자리걸음 move 반복, 자리에 없는 사람에게 말 걸기, 런타임 에러·중단이 없어야 합니다. 주석에서 말한 효과는 트레이스에 실제로 있어야 합니다.
  • 사람이 직접 돌려 보기. Josh가 통과한 장면 일부를 실제 렌더러로 재생합니다. 첫 dev 실행은 전부 보고, 이후 실행은 L1+L2 통과분 중 정해진 비율(예: 10%)만 봅니다.

단계별 거르기(의견).

  • L1은 L0을 통과해야 실행합니다.
  • L2는 critical L1 assertion을 모두 통과해야 실행합니다. Mara가 움직이지도 않은 장면에 저지 비용을 쓸 이유가 없습니다.
  • L1에서 떨어진 것 중 무작위 ~10%도 L2와 Josh에게 보냅니다. L1이 좋은 장면을 잘못 떨어뜨리지 않는지 확인하기 위해서입니다.
  • 레이어마다 따로 보고합니다(Clembench 방식): L0 통과율, L0 통과분 중 L1 통과율, L1 통과분 중 L2 통과율, 그리고 K개 샘플 기준 pass^K.

3.4 (d) 싸게, 정직하게, 계속 키우기

비용. 생성 비용은 Josh가 직접 잰 값입니다 [H].

  • 호출당 평균 실제 비용: Astra ≈ $0.019–0.033, Fable ≈ $0.076, DeepSeek V4.1 Flash ≈ $0.0005.
  • 케이스 26개 × K=3 한 바퀴는 78 × $0.03 ≈ Astra급 $2.3 정도입니다(계산한 추정치).
  • L0과 L1은 비용이 들지 않습니다.
  • 저지 비용은 L1 통과 케이스당 작은 모델 호출 1회 정도입니다. 케이스의 질문을 한 번에 묶어 보내기 때문입니다. 생성 호출 한 번과 같은 자릿수입니다(의견이며 잰 값이 아닙니다).

싸게 만드는 요령(의견, PoLL과 위의 단계별 거르기에서 빌림).

  1. 단계별 거르기. 위와 같이 L0 → L1 → L2 → L3 순서입니다. 싼 모델의 실패 대부분은 L0이나 L1에서 무료로 걸러집니다.
  2. 싼 저지 먼저. 다른 계열의 작은 저지로 시작합니다. 강한 저지(또는 3모델 패널)는 세 경우에만 부릅니다: UNKNOWN이 나왔을 때, 싼 저지 둘의 판정이 갈렸을 때, 정해 둔 10% 감사 샘플일 때.
  3. 판정 캐시. 키는 sha256(rendered_log + question + judge_model_id + judge_prompt_version)입니다. 바뀌지 않은 트레이스는 다시 돌려도 비용이 없고, 프롬프트가 바뀌면 캐시가 깔끔하게 무효화됩니다.
  4. 실행 주기와 규모.
    • 변경할 때마다: dev 스플릿, K=1, L0+L1만.
    • 매일 밤 또는 머지 전: dev+test, K=3, L2 포함.
    • 마일스톤: hidden 스플릿, K=5, L3 쌍까지.
  5. 저지 호출 묶기. 질문마다 따로 부르지 않고, 케이스마다 질문을 모두 묶어 한 번만 부릅니다.

모든 저지는 Josh 라벨로 검증합니다. L2 LLM 저지, 판정만 하는 싼 분류기 저지(X에 이런 제품을 소개하는 포스트가 있지만 정확도 주장은 검증되지 않았습니다: §X.6), 패널, 저지 역할을 하는 키워드 체크가 모두 대상입니다. 숫자를 믿기 전에 같은 Josh 홀드아웃 라벨로 TPR/TNR과 κ를 재고, 무엇이 바뀔 때마다 다시 잽니다. 싸든 비싸든 저지는 분류기입니다.

저지 변화 감지.

  • Josh 라벨이 붙은 렌더링 로그 30–50개 정도로 **기준 세트(anchor set)**를 고정합니다. 통과와 실패를 섞어 둡니다.
  • 저지 모델 id, 저지 프롬프트, 루브릭이 바뀔 때마다 기준 세트를 다시 돌립니다. 바뀌지 않아도 매달 돌립니다.
  • TPR이나 TNR이 약 0.1 넘게 움직이거나, κ가 보정 때 정한 범위 아래로 떨어지면 경고를 띄웁니다.
  • 정확한 모델 ID를 고정하고, 채점 기록마다 남깁니다.
  • 저지 버전이 다르면 L2 숫자를 서로 비교하지 않습니다. 비교하려면 두 시스템을 같은 저지로 다시 돌립니다. Chip Huyen도 저지가 다르면 시간에 따른 점수를 비교할 수 없다고 말합니다(aie-book summaries) [M].

  • 평균뿐 아니라 한 케이스의 변형 간 편차도 보고합니다. 원본은 통과하는데 뒤집은 맵에서 떨어지는 모델은 연출을 배운 것이 아닙니다.

믿으면 안 되는 것.

  1. "state pass"를 연기 품질로 보는 것. Josh의 데이터가 이미 둘이 다르다는 것을 보여 줍니다.

  7. N≈25에서 약 15점 미만 차이. 노이즈입니다(§2.5).
  8. 아무도 검토하지 않은 합성 변형, 그리고 LLM이 쓴 assertion.
  9. not_heard_by 같은 키워드 체크 단독. 투박하므로 저지 질문으로 보강합니다.
